# Running MiniBench rounds

MiniBench rounds start every other Monday and run two weeks with about 60 questions. The active round is always the project `minibench`; between rounds it lists nothing. A finished round is a question series named for its start date, such as `minibench-2026-10-05`. The round opening on 19 October 2026 is Sibyl's first scored entry; the [decision record](../decisions/2026-10-18-first-minibench-round.md) says what was changed for it. [Metaculus FutureEval resources](https://www.metaculus.com/notebooks/38928/docs.adj.news)

## Launch gate

A round is covered by the polling loop below. Each pull is the ordinary command with a grant budget and an archive, `python -m sibyl minibench --tier prod --one-at-a-time --max-questions 5 --grant-budget-usd 20 --archive-dir backtests/minibench_runs`; see [experiment-funding.md](experiment-funding.md). It runs the same research and models as any production run. Runs made with the earlier separate grant runner, which used one research provider, are their own configuration era; it ends when the [one-forecast-route change](../decisions/2026-10-14-one-forecast-route.md) merged. Three questions is a paid smoke run, not a statistical experiment.

Before each paid run, verify that the deployed commit is the intended clean commit; confirm the routed models and reasoning parameters are currently available; confirm the grant key is distinct from the ordinary keys; inspect `python -m sibyl.ops.experiment_grant report` for the remaining local allocation; choose a run ID, question cap and grant budget. A scored, paid run needs the operator's approval for that specific run. Do not dispatch a workflow or enable a schedule as a substitute.

`--archive-dir` writes a private manifest and selected-question snapshot before forecasting, and successful reports after the batch returns, under `<archive-dir>/<run-id>/`. Keep that directory with the spend ledger. After the run, run `python -m sibyl.ops.experiment_grant reconcile --run-id <run-id>` and check the report for confirmed and estimated charges, failed questions and forecaster drops. If the process stops mid-batch, a manifest and ledger can exist without saved reports; reconcile against Metaculus before interpreting missing rows.

## Running a round

Per Metaculus, each MiniBench question launches at a random hour and is open for about three hours. Usually five or fewer are open at once, occasionally about ten, and most launch in a round's first few days. `python -m sibyl.ops.minibench_loop` covers a round from the operator's machine. Every 15 minutes it starts one `python -m sibyl minibench --tier prod --one-at-a-time` run. That run sorts the open questions this bot has not forecast by scheduled close, then forecasts them one at a time; any question that closed while it waited is skipped. Runs never overlap: a pull that comes due while a run is still working through its queue is skipped. Each run takes the literal settings of the MiniBench workflow's run step, so a local run uses the workflow's method.

Run it in a visible terminal from a clean checkout of the intended commit; from a worktree, point `--ledger` and `--archive-dir` at the main checkout's `backtests/`, so the grant's history stays in one ledger. Keep the machine awake (`caffeinate -dims` in front of the command) and plugged in: the loop stops with the machine. It refuses to start without that ledger, without the grant key, or while a `.env.local` would override the workflow's settings. It names any other credential the workflow has and `.env` lacks, and runs anyway: that provider is skipped. It stops before a run whose budget would take the loop's total grant use past `--round-budget-usd`; when the grant's local remaining allocation, less one run's budget, would fall below `--stop-below-usd`; when the personal key has paid more than `--max-personal-usd` across its runs; when a run is refused; or at `--until`. `--mode test --tier free --once` rehearses for nothing: the free roster, no grant, the same loop and ordering, publishing to the bot-testing area. The free tier switches off the paid search providers and both gap-fill passes, so it checks the loop and publishing, not those. `--mode test --once` is the paid rehearsal: one pull through the same loop, settings, grant and ordering against the unscored bot-testing area, which re-forecasts its questions every time and publishes there. Each run's grant budget (default $20 for up to 5 questions) must cover its questions plus the holds of calls in flight, since a run that exhausts it sends the rest of its calls to the personal key. Output streams to the terminal and is kept in `backtests/minibench_runs/<loop-id>.log`. Every run spends and publishes to a scored tournament, so start the loop only with the operator's go for that round.

### The first round's settings

The paid rehearsal on 2026-10-18 cost $1.61 a question before the MiniBench cost cuts; with AskNews and the cuts, expect about $1.25 (an estimate). With $85 left in the grant's local allocation, the round runs with `--round-budget-usd 80 --stop-below-usd 5` and the default 5 questions on $20 a run: no run starts once the loop has used $60, so the round spends $60–80 and covers roughly 48–64 questions. Check `python -m sibyl.ops.experiment_grant report` before starting, and adjust the cap to what is left.

## What the first round can establish

One bot configuration on one round is a descriptive baseline. Record the scheduled question IDs, forecast timestamps, configuration and code identity, question type, any fallback or degradation, published forecast, and final resolution. Do not use a leaderboard rank or a three-question smoke run as evidence that a prompt change worked. Do not tune the seasonal FutureEval holdout against MiniBench feedback.

For a later treatment claim, register the exact two arms and identical question set *before* forecasting. Name one primary endpoint for each question type being tested, an expected effect, an independent variance estimate, allowed attrition, and the minimum detectable effect. Decline a run when the expected effect is smaller than its prospective MDE. Preserve Brier and log scores for binary questions, and report numeric and multiple-choice endpoints separately; pooled scoring remains pending. Pair forecasts by question ID and valid forecast time, report every excluded question and why, and apply the existing greater-than-5% attrition refusal. Report paired deltas with bootstrap intervals and treat repeated looks and multiple tested variants as exploratory unless the registration accounts for them. See [eval-strategy.md](../strategy/eval-strategy.md) and the offline [power preflight](../../sibyl/eval/power.py).

After resolution, the read-only collector can freeze the selected questions' official API records, including outcomes when the API exposes them, without using the comments endpoint. Give each collection a new output path so an earlier snapshot is preserved:

```bash
python -m sibyl.eval minibench-live collect \
  --run-dir backtests/minibench_runs/<run-id> \
  --output backtests/minibench_runs/<run-id>/resolutions-2026-10-20.json
python -m sibyl.eval minibench-live score \
  --run-dir backtests/minibench_runs/<run-id> \
  --snapshot backtests/minibench_runs/<run-id>/resolutions-2026-10-20.json \
  --output backtests/minibench_runs/<run-id>/scores-2026-10-20.json
```

`score` is offline. It counts selected questions with missing forecasts, missing or unresolved outcomes, invalid scores, and reported degradation; it emits separate per-question endpoints and descriptive means over all valid published forecasts, including degraded ones, with no inferential verdict. A read-only check on 2026-10-03 confirmed that the pinned Metaculus client can fetch a matching past MiniBench question by post ID. Five sampled questions marked resolved had no outcome value in the API response; the checked example had not been forecast by this bot. [Metaculus's API policy](https://www.metaculus.com/api/) grants resolution access for closed questions the authenticated account predicted on. The scorer records any resolved question with an absent outcome as `resolved_without_outcome` rather than imputing a result. Verify outcome visibility after the next round and reconcile any published forecast missing from the local archive before using scores. The older performance collector's `/api/comments/` request has returned 403 for the bot token; this path does not use it.

The current `compare` command reads backtest artifacts, not live MiniBench reports. A registered, same-question live paired comparison is still unimplemented. MiniBench results remain descriptive until that comparison path and its prospective power gate are validated; do not label a live variant comparison confirmatory on the strength of the offline backtest gate.
